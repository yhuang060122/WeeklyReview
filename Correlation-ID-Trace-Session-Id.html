Correlation ID × Trace-Session-Id

单请求跨服务追踪 vs 单登录会话追踪

A

一句话结论

核心区别

Correlation ID：每次 HTTP 请求一个，跟着请求在服务间透传，请求结束即消失。 Trace-Session-Id：每次登录一个，跟着浏览器 tab 走，登出或 TTL 过期才失效。

比喻：

  • Correlation ID = 外卖单号：一单从出餐到送达，各环节记同一个单号；单号随这一单结束。
  • Trace-Session-Id = 酒店入住单：入住发一张房卡，住店期间所有消费记同一账单；退房作废，逾期自动失效。
B

Correlation ID 生命周期

  • 入口（网关或首个中间件）没有则生成，有则沿用。
  • 服务间透传：每次调用下游都带上同一个 header。
  • 请求结束等于生命周期结束，无需显式删除。

D

为什么用 AsyncLocal

环境上下文（ambient context）

AsyncLocal 的值随异步控制流流动：同一个请求即使换线程，await 链上的代码仍能读到同一 ID。

  • 作用：免去层层传参，日志、数据库、下游调用都能直接取。
  • 代价：隐式依赖，签名看不出；测试需显式设置；异步泄漏要警惕。
E

后台服务能用中间件吗

结论

能拼管道，但示例做法不地道。中间件依赖 HttpContext；后台服务没有 HttpContext，IHttpContextAccessor 为 null。

  • 正解：任务入口直接设置 AsyncLocal，或显式把 Correlation ID 传给下游。
  • 不要为了"跑中间件"在后台服务里启动 WebApplicationBuilder，那是绕远路。

分层最佳实践

会话级Trace-Session-Id（本仓库）
  • 请求级Correlation ID / OTel TraceId
    • 操作级SpanId（单服务内一段操作）
  • 三层叠加：按"会话"拉全量日志，按"单请求"看链路。
  • 与 OpenTelemetry 的关系：TraceId ≈ Correlation ID；Trace-Session-Id 是其上的会话容器。
