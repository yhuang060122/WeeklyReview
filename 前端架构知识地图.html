① 六边形架构落地：Slice 文件组织法

文件夹的名字 = 业务功能的名字（Screaming Architecture）；读写分离，依赖永远指向内部。

Feature Slice

  • list-flashcards/ → query：controller + dto + query 服务，直接查 DB，不走领域层
  • notify-answer/ → command：写操作走领域模型
  • flashcard.module.ts → Bounded Context 根组合

model/（领域层 · 最内层）

  • 纯实体：box.entity / flashcard.entity
  • 定义端口：box.repository、date-provider 接口
  • 不 import 任何 infra —— 依赖指向内部

infra/（适配器 · 最外层）

  • 仓储实现：postgres / inmemory 各一套
  • prisma.service、real/stub date-provider
  • 测试可注入 stub，无真实 IO

四大优势

  • Screaming Architecture：看目录即知功能
  • Collocation：改一个功能只进一个目录
  • 无 ports/adapters 技术术语文件夹
  • 轻量 CQS → 可演进为 CQRS
▼每个微前端内部仍可用 Slice 组织 —— 外层部署边界 ⊃ 内层代码边界
部署尺度 · 应用间

② 微前端 + Module Federation

微前端解决"拆"（独立部署、团队自治），Module Federation 解决"运行时合"（动态加载、共享依赖）。

Host 宿主

  • 消费并集成远程模块的主容器
  • 负责编排、运行时动态加载
  • 可同时暴露自己的模块 → Bidirectional Hosts（双向宿主）

Remote 远程

  • 独立开发、独立部署、可跨域名
  • 暴露组件 / 函数 / 资源
  • 被 Host 在运行时消费渲染

五大收益

  • 按需增删模块 → 可扩展
  • 独立发布 → 低耦合风险
  • 自选技术栈 → 团队自治
  • 懒加载 + 共享缓存 → 性能
  • 组件跨应用复用

挑战 → 最佳实践

  • 内聚难 → 小而聚焦
  • 通信难 → 公共 API / 事件总线
  • 部署复杂 → 集中配置 + 版本控制
▼应用上线后，一切运行行为进入观测层
运行尺度 · 线上

③ 前端监控体系：可观测性闭环

把"用户看到的、浏览器经历的、业务发生的"变成结构化数据，走完五环节闭环。

三类目标

  • 稳定性：JS 错误 / Promise 异常 / 资源错误 / 接口错误 / 白屏
  • 体验：加载性能 / 卡顿 / 交互延迟
  • 业务：PV / UV / 停留时间

五环节闭环

  • ① 前端埋点 → ② 数据上报 → ③ 加工汇总
  • ④ 可视化展示 → ⑤ 监控报警
  • 报警 → 修复 → 再埋点（反馈回路）

埋点三方案

  • 代码埋点：精确但工作量大
  • 可视化埋点：系统代替手工
  • 无痕埋点：全量数据，压力大

错误捕获四通道

  • error + target.src/href → resourceError
  • error（捕获阶段）→ jsError
  • unhandledrejection → promiseError
  • 重写 XHR open/send → 接口异常
↺ 闭环：监控报警 → 定位到具体 slice / 具体 remote 模块 → 修复 → 重新部署 → 监控验证

Node 监控九维度

维度关键信号
日志异常类型/数量变动
进程工作进程数低于阈值
内存只升不降 = 泄漏

CPU Load1/5/15 分钟平均负载
磁盘 / I/O / 网络用量上限 + 流量预警
应用状态 / DNS健康检查接口 + 域名探活

内存泄漏四来源

来源典型场景
全局变量window 挂载数据
被遗忘的定时器setInterval 未清理
脱离 DOM 的引用已移除节点仍被持有
闭包外部引用未释放
